# Destiny Garden WebGL 音声調査（2026-11-15）

提出コードは `8685b7d56b3c388bcc0938d92bda0aac7c20c00e`。提出ZIPのSHA-256は `d8103e818f07187624e137dcc1535a7e4bbc35ef483326f98da6a8106dd968fb` と一致した。itch.ioから取得したWasm・データ・音声を含むJSは、ZIPのgzipを展開した結果とバイト単位で一致した。ローダーも一致し、HTMLの差はitch.io側が追加したスクリプト1行だった。

作業開始時のiMacの空き容量は94 GiB。提出版を展開したローカルコピーと、別worktreeの開発用ブランチで確認した。比較ビルドには提出時と同じUnity 6000.3.23f1、WebGL 2、1280×720を使用した。

## 再現した条件

- MacのChrome 157で、未操作のタイトルはAudioContextが `suspended`。ゲーム画面の初回クリックで `running` になり、画面遷移と投擲は進んだ。入場後の環境音と投擲後の効果音は、いずれも出力点でRMS・ピークともに0だった。タイトルで13.5秒待ってから最初のクリックで入場した場合と、Mac上のWebKit試験でも入場後と投擲後の出力は0だった。
- `AudioDestinationNode` へ接続された各ノードを、既存の接続に並列でアナライザーへ接続した。接続と切断を追い、比較の前後に同じAudioContextの出力点へ3 kHz、振幅0.02の正弦波を流した。前後ともRMS 0.0141421、ピーク0.02を測定し、テスト音停止後は0に戻った。
- 提出版で、数十本の生成済みPCMバッファすべてに波形があった。UnityのWebAudioバックエンドではループ音と投擲時の音が再生中として登録されていたが、出力に接続した各チャンネルのゲインは0だった。CoreAudioの出力稼働フラグはChromeのストリームが開いている間にも立つため、波形や聴取の証拠には使わなかった。
- 独立したChromeプロファイルで、計測対象タブのデバッガ接続を閉じて通常の別タブへ切り替えた。5秒ほど非表示になった間は描画フレームが止まり、AudioContextの時刻は進み続けた。復帰後にはフレームが再開した。前面でも同じ無音だった。ブラウザを強制停止・復帰させる試験は、macOSの画面ロックとは別に記録した。

## 原因と開発用の修正

`GardenScene` が実行時に作るカメラに `AudioListener` が付いていなかった。Git内でリスナーが付いていたのは、このWebGLビルドに含まれない `SampleScene` のカメラだった。メインカメラを生成する `GardenView.Build` でリスナーを1つ付ける。既存の音源、音量設定、ゲーム側の操作、バックグラウンド実行設定は従来の構成を使う。[UnityのAudio Listener資料](https://docs.unity.com/en-us/engine/6000.3/manual/audio/reference/class-audio-listener)

提出版で使われる音は、実行時に生成した非圧縮PCMとしてWeb Audioに渡る。UnityはiOSブラウザの消音モード中にこの種類の音声が聞こえない場合があると案内している。今回のMacでの再現とは別の条件であり、投稿者の端末や設定は不明。iPhone実機は調査時にオフラインだった。[UnityのWeb音声資料](https://docs.unity.com/en-us/engine/6000.3/manual/platform-specific/webgl/develop/audio#issues-with-silent-mode-on-ios-browsers)

## リスナー有無の比較

診断版は同じWasmを使用し、起動時にカメラへリスナーを付けるかどうかだけを切り替えた。タイトルをクリックする前は両方とも `suspended`。クリック後は両方とも `running` になった。

| Chromeでの測定 | リスナーなし | リスナーあり |
| --- | ---: | ---: |
| 有効な `AudioListener` | 0 | 1 |
| `AudioClip.SetData` がtrue、かつ `loadState=Loaded` の件数 | 49 / 49 | 48 / 48 |
| Unityの波音・ベルの `AudioSource.isPlaying` と音量 | true・0.104 / true・0.8 | true・0.104 / true・0.8 |
| ブラウザの最終ミックス、初回クリック後のタイトル（最大RMS） | 0 | 0.01774 |
| 同、入場後（最大RMS） | 0 | 0.01574 |
| 同、投擲直後（最大RMS） | 0 | 0.18395 |

効果音の種類が出目などで変わるため、作られたクリップ数は回によって異なる。上記の両方でゲームの初期音量は0.80、ミュートはfalse、`AudioListener.volume` は1.00、`AudioListener.pause` はfalseだった。リスナーを付けると、Web Audio側でも波音のチャンネルに約0.104のゲインが渡った。アナライザーはWeb Audioの出力直前の信号を測っている。内蔵スピーカーから実際に鳴った音は遠隔から聴取していない。

診断版のChromeでは `Application.runInBackground=False` をUnity側で記録した。約5.3秒の別タブ表示中はUnityのUpdateが1回も進まず、その間も音声処理の時刻は約5.1秒進んだ。タブ復帰後は追加入力なしで環境音の信号を確認し、続けて投擲音も確認した。開発者向けプロトコルでページを強制停止させ、再びページを表示する試験でも、描画と音声信号が復帰した。

診断版のゲーム内ミュートでは出力RMSが0になり、解除後に波形が戻った。WebKitでも、`AudioContext.suspend()` で音声処理を止めたあと、実際のクリックによって `running` と新しい波形が戻った。停止中はアナライザーに直前のサンプルが残るため、状態と処理時刻が進んでいることも併せて確認した。

## 開発版の確認

- 診断コードを除いたビルドで、Chromeは入場後0.01782・投擲後0.18794、WebKitは入場後0.01874・投擲後0.18302の最大RMSを記録した。Chromeのゲーム内ミュート中は0で、解除後は再び波形が出た。通常のタブ切替と、ブラウザのページを強制停止させてからタブを表示し直す試験でも復帰を確認した。
- macOSの実際の画面ロックと解除、iPhone実機の消音モードON/OFF、スピーカーでの聴取は未確認。投稿者の条件は特定できていない。
