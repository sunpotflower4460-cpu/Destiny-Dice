## 2. 配面が庭へ応答し、多様性を保つこと

### 2.1 局所的な判断の反例

水の直接作用先が十分に湿り、遠くの別領域だけが乾燥している庭を用意する。遠方の土をさらに乾かしても、そのレシピの作用先・予定dose・局所必要度は変わらないので、水の候補重みは変わらない。

逆に、雨だけが直接届く近傍土セルを適湿下限より乾かせば、雨の必要度だけが増し、しずくの必要度は変わらない。共通のanchorセルを乾かす場合は両方へ影響する。v0.2の雨は、しずくの直接作用先を含む範囲だからである。風の重みも、実際に風が届く場所の過湿から求める。遮蔽で実効doseが0のセルを、必要度の平均へ混ぜない。

これは「最もよい結果になる入力を先読みするAI」ではない。[GAMEPLAY.md](./GAMEPLAY.md)の固定した局所指標を使い、出目が決まった後は[SIMULATION.md](./SIMULATION.md)の自然モデルで結果を計算する。

### 2.2 配面分布の参照計算

8レシピがすべて候補、各系統2レシピ、系統の重みは候補レシピの平均、3系統を重み付き非復元で選び、残り3枠を個数制約付きで埋める条件で分岐を全列挙する。最後の面番号シャッフルは各系統の面数を変えないため、面数の集計では省略できる。

| レシピ重みの条件 | 一つの配面に含まれる水の平均面数 | 水の面が3個になる確率 | 水の面が0個になる確率 |
|---|---:|---:|---:|
| 全レシピ100 | 1.500000 | 約10.0965% | 約9.5863% |
| 水の2レシピ300、他の6レシピ100 | 約2.290383 | 約42.4995% | 約0.5219% |

重みを上げると水を含みやすくなる一方、**水だけの6面にはならない**。3系統以上、同系統3面以下、同レシピ2面以下の制約を残す。これは静的な候補重みに対する設計計算であり、変化する庭での実プレイ頻度や、水を願うことで出目が変わることの測定ではない。

参照計算は有理数で676個の最終recipe個数状態を集計し、両条件とも確率総和1を確認した。平均面数の厳密値はそれぞれ`3/2`、`187067/81675`。丸めた表の値を実装の判定条件には使わない。

実装時は別に、同じ保存byte列から同じ配面が得られること、重み0や候補不足の設定を拒否すること、種の候補がない庭でも水・風・光の3系統を満たすことを確認する。

## 3. 同じ自然入力が違う結果を生むこと

数式・単位・丸め・更新順の正はSIMULATION。数値の全入力・端数・期待値はfixture JSONを参照する。

### 3.1 風と湿り

単セル、初期地表水0、基礎光500、初期成長0、端数0、40tickの参照例では、同じ風1000が次の違いを生む。

| 初期土中水 | 無風での成長 | 風1000での成長 | この例で確かめること |
|---|---:|---:|---|
| 950（過湿） | 20 | 184 | 蒸発で湿りが適湿へ近づき、成長条件が改善する |
| 250（乾き気味） | 233 | 101 | 同じ蒸発で湿りが不足し、成長が遅くなる |

成長はゲーム用整数単位。「風を引いたので成長ボーナスを与える」という別の規則を足さず、蒸発→湿り→成長の同じ式で結果を変える。岩陰の風の例もJSONに含める。

### 3.2 入力の順番

同じ初期土中水600、同じ合計80tickで、種→光では成長1500、光→種では成長500になる参照例を含める。両方とも最終土中水は540。種を置く前の光を後から成長へ足さず、前回の光入力も永久に蓄積しないことを確かめる。

### 3.3 水の保存と長時間運転

- 手元の水がない高いセルから水を作らない。流出は辺ごとの上限だけでなく、セル全体の予算内に配分する。
- 地表と土から同じ蒸発要求を二重に引かない。水がない間の未消費要求を「蒸発の借金」にしない。
- 排出口の例では、高さ100・水300・堰高250・毎tick上限100から、最初に100、次に50を排出し、水150が残る。排出を水収支へ含める。
- 展示庭では最大注水を200回続け、各tickの水収支、全セルの非負・上限、排出口への接続、根元と入口の水位を確認する。排出口の容量の式だけでは、実地形の滞留や溢れを保証しない。

### 3.4 一つの庭で読む三つの関係

| 庭の部分 | 開発用入力で確認する場面 | 表示するもの |
|---|---|---|
| 乾いた入口、傾斜、下流の湿った土 | 最初の水が土に入り、次の水は一部が先へ届く | 実際の水と吸水。経路未追跡なら経路を断言する文章は出さない |
| 湿りすぎた区画、風上の岩、岩の背後 | 同じ風でも露出部と岩陰で蒸発が異なる | 同じ風量場による葉の揺れと、記録された湿りの変化 |
| 湿ったつぼみ、明るい場所と日陰 | 水と光の条件が揃った個体だけ段階が進む | 閾値を越えた個体の一度だけの成長アクセント |

この固定入力は地図の受け入れ確認用。通常の投擲へ混ぜたり、開花のために出目を補正したりしない。最初の数投の見やすさは、地図・段階・係数・構図で調整する。

### 3.5 v0.3の全庭参照計算

具体的な配置と全結果は[GARDEN_LAYOUT.md](./GARDEN_LAYOUT.md)とreport JSONに置く。profile v0.2の係数を使い、地図の浅い入口・土・岩・光の露出・初期個体を展開した独立した整数計算である。

| 参照ケース | 計算した範囲 | 確認できたこと |
|---|---|---|
| 各recipeの単発 | 8入力×40tick | 初期の8入力の作用先、全庭の状態と収支 |
| 入力の順序 | 水→水→光、種→光、光→種の計7投 | 同じ総時間でも、入力の順と開始状態で結果が変わる |
| 最大量の連続注水 | drop 200投、rain 200投 | 全tickの収支・上限、排出口の作動、最大水位 |
| 固定した抽選列 | seed番号0～15の全16列×24投 | 384配面の制約、庭の違い、成長しなかった投擲も含む結果 |

計799投・31,960tickで水収支残差0と状態範囲内を確認した。連続注水の初排出はdropの41投目、rainの37投目。累計排出は35,082と40,116で、短い抽選列では排出は起きなかった。排出口があることと、少数の投擲で必ず排出することを混同しない。

16列の初開花は2～3投目だった。これは初期つぼみと、全投擲で進む40tickの基礎成長の寄与を含む。最終の花は5～13、整数成長量が増えなかった投擲は合計16回だった。これらの列の結果を、通常プレイの開花保証や、祈りの効果の測定値へ置き換えない。

SHA-256の役割別counter列から作る固定byteは再現用fixtureであり、本番の乱数取得やその品質検定ではない。reportは使用map/profileのhashと全seedの結果を残す。通常プレイへ特定の出目列を流し込まず、G2では同じ入力をC#で再計算する。

## 4. 言葉と演出が同じ事実を指すこと

カードは出来事を追加せず、成立しているObservationGroupの中で焦点を選ぶ。条件に適合する文章が複数あるときだけ、カードとの対応・優先度・直近の重複で選ぶ。全述語の定義はGAMEPLAYに置く。

| 入力と記録の例 | 選んでよい内容 | 選んではいけない内容 |
|---|---|---|
| 元から湿った土へ水が入り、土中水が増加 | 土が水を受け取った | 「乾いた土」が潤った |
| 種を置いたが発芽閾値に未到達 | 種が土に置かれた | 芽が出た、根が広がった |
| 途中で吸水したが、蒸発後の土は事前より乾いた | その区間に土が水を受け取った | 終状態が潤っている |
| 開花イベントはあるが、今回の光入力はない | つぼみが開いた | 今回のひと筋の光が花を咲かせた |
| 根元の土が湿ったが水路の由来は未追跡 | 根元の土が湿った | 岩を回った水が、この根へ届いた |
| カードが欠け、自然入力は確定・解決済み | 実際の入力に対応する事実fallback | 新しいカードを引いて埋める、架空のカード名を添える |
| 同groupの2個体が、同じ文の全条件を満たす | 固定bindingKeyで一つの完全な根拠束を選ぶ | 述語ごとに別個体の先頭一致を選ぶ、列挙順で変える |
| 離れた2か所で水が動き、全域集計が一つある | 一つのglobal groupとして庭の水の動きを述べる | 同じ累計輸送量を2groupへ複写、片方の到達量とする |
| 二つの種を比較する文と、別の場所の開花が成立 | 二つ目の種groupを必須の補助焦点にする | 開花の派手さで補助を置換し、文の対象を見失わせる |

各入力に一つ以上ある事実fallbackは、稀な現象やカードの一致を条件にしない。自然の変化を述べる候補がなくても、入力の実適用を確認できた場合はその系統の固定文を使える。選択済みの入力名だけでは補完せず、適用証拠が欠ける場合は保存・回復の経路へ戻す。

音と光は主焦点1つ、副焦点1つ以下。開花が複数あっても、成長音を個体数だけ重ねない。集約前のモデル上の事実・量を消す処理とは分ける。低刺激設定や演出スキップでも、出目・庭・文章の事実は同じである。

## 5. 中断しても記録の意味が変わらないこと

以下は[DATA_CONTRACT.md](./DATA_CONTRACT.md)の実装時に試す境界。G0ではI/O実装がないため、強制終了試験の合格結果ではない。

| 止める・競合させる場所 | 期待する経路 |
|---|---|
| 配面の取得開始記録だけが残る | 配面準備の中断として記録。出目の欠測へ混ぜない |
| 配面材料は保存済み、Preparedは未保存 | 保存材料から同じ6面を作る。新規材料を取らない |
| 意図の保存中に取消 | 同じコマンド列で順序を決め、取得開始前の取消が確定したなら取得しない |
| 取得開始の後に画面を閉じる | 出目の処理は継続。取消を理由に既知結果を欠測へ戻さない |
| 出目・カードの材料は保存済み、Outcomeは未保存 | 保存材料から解釈して確定。未表示を欠測とみなさない |
| 出目は有効だがカード材料が利用不能 | 出目を保ち、カード欠測と事実fallbackを記録 |
| Resolvedのframeが途中で途切れる | 元segmentを保全し、検証済みheadから新segmentへ継続 |
| 回復処理中にもう一度終了 | 同じ回復IDへ収束し、継続先や結果を二重に作らない |
| 履歴途中のhashが不一致 | 通常の末尾回復へ進めない。過去を切り捨てて正常と表示しない |
| Resolved後、提示記録前に終了 | 同じ庭と文章を保持。読んだ／読んでいないを断定しない |
| content blobの保存失敗 | その参照を持つRunStartedへ進まない |
| 同じ庭から、異なるroundIdで同時に準備 | 一つだけ開始。未終端枠がある間は別roundの開始を拒否 |
| 開始時と異なるworldRevision/hashでResolvedを保存 | 古い計画を採用せず、最新の庭を上書きしない |
| 次の準備中に前回の提示Receiptだけが届く | journal headと庭の参照を区別し、庭が同じなら誤って不整合としない |
| Resolved保存後、画面は途中の水流を再生中 | 次のPreparedは非公開。終状態を表示してから公開・意図編集・Rollを許可 |
| 省略・閉じる操作のreleaseと次の公開が重なる | 旧gestureを消費し、次の投擲には新しいpressを要求 |

## 6. 振り返りの分母を見失わないこと

水を目標にした10回のうち、水の面がない回が9回、残る1回だけ水を引いた場合、比較対象では1/1になる。この表示の隣に、意図確定10・比較対象1・p=0の9回を示す。「願いが10回とも叶った」という意味へ変換しない。

各回の固定済み配面から得た`p_t`で基準値を求める。出目が保存済みなら、庭の解決や提示が途中でも既知結果を除外しない。欠測を0や1で埋めず、観測した集合とその基準値を揃える。

庭の関係図は、自然入力→局所状態→適用ルール→結果を結ぶ。意図・カード・出目の順序と対応は別の記録として示す。初めての発芽などの「発見」も、この履歴から再生成できる表示とし、別の手動報告を求めない。

今回の追加入力が届かない植物が、事前の水分と基礎光によって開花する反例も用意する。「40tickの経過・基礎光」「開始時の状態」「今回の追加作用」を区別し、roundが同じという理由だけで入力から開花へ矢印を引かない。イベントのinputRefだけでは局所的な因果関係の証拠にならない。反実仮想の別シミュレーションや水粒子の由来追跡を、最小版の成立条件に追加するものではない。

## 7. 人の目と耳で確認する残り

自動照合で手作業を減らし、人は次の5点を展示端末で確認する。
操作の具体的な場面は[EXPERIENCE.md](./EXPERIENCE.md)§9に対応させる。

1. 六つの面と、入力が届く場所を迷わず見つけられる。
2. 水の移動・岩陰の風・成長の違いを説明なしでも追える。
3. 日本語が自然で読みやすく、カードと光・音が同じ変化を指す。
4. 消音・低刺激設定・連続投擲でも、静けさと操作の分かりやすさが保たれる。
5. 起動、中断、再開、履歴、新しい来場者への切替を実機で通せる。

確認したビルド、端末、設定、結果は[PROGRESS.md](../../PROGRESS.md)へ追記する。細かな見た目を調整しても、既知結果・保存順序・自然の保存則を変更しない。
