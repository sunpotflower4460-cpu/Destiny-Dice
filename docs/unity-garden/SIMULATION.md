# 庭の自然モデル

設計版0.1。すべてゲーム用に単純化したモデルの設計であり、現実の流体・気象・植物生理を精密に再現したという主張ではない。以下の数値は試作用の初期値で、実装・実機検証は未実施。

## 1. モデルが作る結果

入力は「水を加える」「風を通す」「光を照らす」「種を置く」。池・発芽・開花を出目から直接発火させない。位置、岩、土の湿り、日陰、過去の成長量に応じて結果を求める。

水は物質、風は作用する場、光は照射量、種は成長可能な個体として扱う。内部を共通の「エネルギー点数」だけで表現しない。

### 初期の計算単位

| 項目 | 初期案 | 意味 |
|---|---|---|
| 地表 | 16×16、セル面積は一定 | 画面の3Dメッシュと計算格子は別 |
| 近傍 | 上下左右の4近傍 | 斜めへ一足で水を移さない |
| 時間 | 1tick = 0.1モデル秒、1投擲 = 40tick | 描画fpsや祈る時間で進行量を変えない |
| 水・地形高 | 整数のモデル単位 | 同じセル面積なので水量から水深を換算できる |
| 光・風・成長の係数 | 0～1000の整数比 | 中間積と総量は64bit整数、除算規則を固定 |
| ゲーム進行 | 投擲の解決中だけ | 待機・バックグラウンドで庭を消耗させない |
| 植物 | 最初は1種類 | 種、芽、葉、つぼみ、花の段階 |

実時間の4秒が現実の植物の4秒に対応するわけではない。展示で変化を見られる速度は成長係数として明記し、乱数結果を変更する方法で調整しない。

## 2. 状態

| 区分 | 必須データ |
|---|---|
| 地図 | `mapId`, `mapVersion`, 幅・高さ、セルの固定順序 |
| 固定セル | `height`, `solid`, `soilCapacity`, `infiltrationPerTick`, `lightExposure`, `plantable` |
| 可変セル | `surfaceWater`, `soilWater`, 直前の解決区間の`meanLight` |
| 個体 | `plantId`, `cellId`, `stage`, `growth`, `originKind`, `seedSourceRoundId?` |
| 系の状態 | `tickIndex`, `lastResolvedRoundId`, 量の出入りの集計 |
| 解決中の入力 | 確定した`recipeId`, 作用セル、量・範囲・方向・残りtick数 |

`solid`セルは水・土・種の受け入れ対象にしない。初期地図の岩の間に少なくとも一つ迂回路を作る。地図は静的な一庭を手で設計し、ランダム地形生成は製品拡張に回す。

### 初期地図fixtureの要件

最初の庭には、上流から低いくぼみへ続く傾斜、岩とその横の迂回路、乾いた土と既に湿った土、明るい場所と岩陰を置く。植物は芽とつぼみを各1個以上、種を置ける空き土は2セル以上を初期案とする。初期配置の個体は`originKind=initialMap`で、存在しない播種roundを割り当てない。

G2ではこの一つの地図を実データにし、各入力の小さな変化が読めることと、水→水→光の開発fixtureを確認する。プレイ中の出目を開花しやすい値へ補正しない。完成した初期地図の状態・成長量もrunの開始時に保存する。

### 作用位置

初期庭には水の入口、風の入口、光の中心、種の散布中心を置く。各レシピの作用セルは`Prepared`時点で解決し、6面すべてのパラメーターに保存する。

種は中心からの格子距離、その後`cellId`順で空き土セルを選ぶ。必要な個数を置けないレシピは配面の候補から外す。その根拠も記録する。水・風・光は庭に定義されたanchorからの作用が常に計算できる地図を用意する。

将来タップで場所を選ぶ場合も、場所変更を配面の固定より前に行う。確定した面の作用先を出目を見てから変えない。

## 3. 1投擲の解決

1. `Prepared`に保存された庭・地図・ルールをロードする。
2. `OutcomeCommitted`の面を取得する。モデル内部で新しい乱数を引かない。
3. その面の入力を適用し、40tickを決まった順序で進める。
4. 各tickで水の出入り、局所状態、成長量を計算し、実イベントを検出する。
5. 更新後の全状態、イベント、メッセージとその根拠を`Resolved`へ一緒に保存する。
6. 保存に成功した計算経過をUnityが再生する。表示のスキップやfps変化でモデルを再計算しない。

モデルの中間状態は表示用に保持し、表示はその間を補間して滑らかにする。粒子の装飾乱数はCoreの水量や成長量を変えない。再起動後、終状態しか復元できない場合はその状態と記録を見せ、見ていないアニメーションのために結果を再生成しない。

各tickの処理順は、予定された水・種の注入、光・風の場の計算、地表水の流れ、吸水、蒸発、個体の成長、閾値イベントの検出とする。流量計算の開始状態は、そのtickの注入後・流れ更新前の状態である。種の配置と水の総量を全tickで繰り返さず、保存済み`injectionSchedule`に従う。

## 4. 水の移動

### 4.1 入力と局所流

水入力は指定されたセル集合へ総量を分配する。分配の整数余りは固定した`cellId`順へ1単位ずつ配り、注入総量を一致させる。入力の総量と1tickあたりの供給量を混同しない。

各tickの開始状態について、セル`i`の水面高を`H_i = height_i + surfaceWater_i`とする。水を通せる隣接セル`j`ごとに、移動希望量を計算する。

```text
rawFlow(i,j) = floor(max(0, H_i - H_j) × conductance / 1000)
```

`conductance`は1tickあたりの係数。初期候補は125。dtを変えるときはこの係数もルール版として見直す。

`sum(rawFlow)`が手元の水量を超える場合は、水量に比例して各方向へ配分し直す。切り捨ての残量は小数剰余の大きい方向から配り、同点時は固定方向順を使う。どの方向にも希望量を超えて渡さない。流出総量は必ず元の`surfaceWater`以下にする。

全セルの流量を**同じtickの開始状態**から計算し、その後で一斉に増減させる。計算途中で隣の水量を書き換えない。

```text
surfaceWaterNext(i) = surfaceWater(i) - outgoing(i) + incoming(i)
```

岩への辺は流量0。初期地図の外周は閉境界とし、庭の外へ水を流さない。将来の排出口は別の境界条件として定義し、流出量を必ず集計する。

### 4.2 吸水、蒸発

流れを更新してから、地表から土へ吸水させる。

```text
absorbed(i) = min(surfaceWaterNext(i),
                  soilCapacity(i) - soilWater(i),
                  infiltrationPerTick(i))
```

地表から引いた量を土へ同量だけ加える。土に余裕がないときは吸水0であり、水を削除して容量へ丸めない。

次に、その場所の光と風に応じた蒸発要求量を計算し、地表と土それぞれの実在量で制限する。小さな蒸発量の切り捨てが恒常的な0を作る場合は、整数の分数残量を状態に保持する。初期版の植物は成長に伴う水消費を追加せず、湿りを成長条件に使う。吸収・蒸散を追加する版では別のsinkとして計上する。

### 4.3 保存則

各tickと投擲全体で、次が一致することを検証する。

```text
地表水 + 土中水 の増減 = 注入量 - 蒸発量 - 境界からの流出量
```

負の水量、容量を超えた土中水、丸めによる水の生成を認めない。整数を使用する初期案では差0を合格条件とする。描画上の水面メッシュの大きさでCoreの水を補正しない。

## 5. 光と風

### 光

静的な地図に、岩・樹木による日陰を表す`lightExposure`を0～1000で持つ。初期版は地図と一緒に確認するデータとし、実行時のGPU影画像を計算の正にしない。

基礎光と、今回の光入力の範囲内減衰を合わせ、遮蔽率を掛けてセルの有効照射量を求める。係数の上限を適用する順序も固定する。光はそのtickの照射であり、前回の光量そのものを永久に蓄える値ではない。光による成長の蓄積は個体の`growth`、光不足の配面判断は直前区間の`meanLight`で表す。

初期版の影は静的。木が伸びたことで影を動的に作り直す機能は追加版とする。表示もこの制限に合わせ、成長した木の新しい影が既にモデルへ影響したような文章を出さない。

### 風

入口からの方向ベクトルと範囲内の強さを持つ。セル中心から風上へ格子線をたどり、岩で遮られた場所は風量を減らす。通過順と遮蔽係数はルールに含める。

風は露出した場所の蒸発と、同じ場を参照する葉・草の表示に作用する。岩の背後で弱まる違いを見せる。渦・乱流・圧力・波の精密計算は含めない。未発芽の種の移動、水による種の運搬は製品拡張に回し、展示版で計算していない運搬を文章に書かない。

## 6. 種と成長

種レシピは、保存済みの空き土セルへ種を1個または複数個置く。初期案では1セル1個体。種を置くことと発芽を分け、直ちに完成した花を生成しない。

各tickで土中水比率を計算し、乾燥・適湿・過湿に対応する`moistureFactor`を0～1000で求める。有効光量から`lightFactor`を求め、両方が成立する程度に応じて成長量を加える。

```text
growthDelta = floor(growthPerTick × moistureFactor × lightFactor / 1000000)
```

分数残量を使う場合は個体状態に含め、プラットフォームで丸め方を変えない。閾値をまたいだときだけ`Germinated`／`LeafOpened`／`BudFormed`／`Bloomed`を出す。同じ段階へとどまるtickで同じイベントを再発行しない。

初期版では乾燥・過湿で成長が遅くなる／止まる。枯死、病気、害虫、栄養競争は追加しない。花は最終段階として残り、全区画が育った後も水・光・風の変化を眺められる。「新しい庭」は新runを始め、過去の庭の履歴を残す。

水量、土の容量、照射量、成長速度・閾値は[G2の検証](./ROADMAP.md)で調整する。単調な「数字が大きいほどよい」にせず、広く弱い入力と狭く強い入力など作用の違いを作る。使われた値は保存する。

## 7. 出来事から演出と文章を作る

イベントには`eventId`, `roundId`, `tick`, `cellIds`, `plantId?`, `ruleId`, `before`, `after`, `evidence`を持たせる。

| イベント候補 | 成立根拠 | 表示できる内容 |
|---|---|---|
| `WaterEntered` | 実際の注入量が正 | 指定地点へ水が入った |
| `SoilMoistened` | 対象セルの土中水が増えた | 土に水が染み込んだ |
| `RootZoneWetted` | 発芽済み個体のセルへ吸水があり土中水が増えた | 根元の土が湿った |
| `PuddleFormed` | 低地の水深が定義済み閾値を下から超えた | くぼみに水がたまった |
| `WindSheltered` | 入力の風が岩の背後で規定以上減衰 | 岩の陰は風が弱い |
| `SeedPlaced` | 個体が有効な空き土セルへ追加された | 土に種が置かれた |
| `Bloomed` | 成長が開花閾値を初めて超えた | つぼみが開いた |

「岩を回って水が根に届いた」という経路文には、流量辺からその経路を確認した根拠が必要。地形の見た目だけで推測しない。展示版で経路追跡を実装しない場合は「根元の土が湿りました」と事実の範囲で表す。

「乾いた土」は事前水分がルールで定めた乾燥閾値未満の場合だけ使う。「届かなかった」などの不成立も、対象・判定区間・該当する流量や状態を確認した場合だけ文章にする。イベントがないことだけから、起きていない現象を推測しない。

同様に「前の雨がこの花を咲かせた」と特定回への因果を断言するには、水の由来を追う追加モデルが必要。初期版は「残っていた水と、今回の光でつぼみが開きました」のように、実際の事前状態と今回の成長条件に基づく文を条件付きで使う。

履歴の関係図は、入力、局所状態、適用された規則、観測された結果を結ぶ。粒子一つずつの由来や、意図が乱数へ作用した因果を計算できる図とはしない。[DATA_CONTRACT.md](./DATA_CONTRACT.md)の観察グラフと区別する。

## 8. 決定性と検証

Coreの入力は、事前状態・確定レシピ・地図・ルール版・固定tick数のみ。同じ入力で同じ出力になることを自動テストする。初期案は整数演算、固定走査順、明示した除算・余り配分で端末差を減らす。Unityの物理サイコロや描画フレームを再現性の根拠にしない。

保存された`Resolved`が過去の正であり、アプリ更新後の再計算で過去の庭や文章を上書きしない。Mono／IL2CPP・iOS／Android／デスクトップ間の一致は実際の共通fixture実行で確認するまで「対応済み」と表示しない。

実装時の合格例:

- 平地2セル、低地、岩の迂回路で水が保存され、岩へ流入しない。
- 同じ注入でも乾いた土と容量近くまで湿った土で、下流へ届く量が変わる。
- 土の吸水容量と流量上限を境界値で確認し、どのセルも負にならない。
- 光の遮蔽、風の遮蔽が同じ配置に一致し、葉の表示もその場を参照する。
- 種は条件が不足すると種のままで、十分な水と光が蓄積すると段階が進む。
- 30fps／60fps、演出省略、再開で最終状態が変わらず、`roundId`を再適用しない。
- イベントの成立条件を満たさないと対応メッセージは候補に入らない。

## 9. 最初の実装で確定するパラメーター

`soilCapacity`, `infiltrationPerTick`, 注入量と範囲、光と風の減衰、蒸発係数、成長適湿帯・閾値、プール容量はG2でfixtureと展示端末の結果を見て固定する。動作を確認していない数値に「自然に見える」「3分で必ず開花する」という保証を付けない。

**最小の受け入れ場面は、最初の水で土が湿り、追加した水がその先へ届き、その湿りと光で種が育つこと。** それを固定入力のfixtureで確かめてから、実際の公平な抽選につなぐ。fixture用の出目列を通常プレイに混ぜない。
