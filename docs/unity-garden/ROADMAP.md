# 実装・展示・製品化の計画

2026-11-11 / G0設計 v0.4。残り約3日という目安は展示準備の制約であり、全プラットフォームの公開期限を保証するものではない。

## 1. 展示で完成させる体験

**一つの庭で、空と動的な配面を見て振り、天候の中へ局所入力が加わり、自然な変化と言葉と記録が残る。**

| 展示の必須範囲 | 上限・初期案 |
|---|---|
| 庭 | 1地図、固定カメラ、植物1種類、段階成長 |
| 自然 | 水と土を中心に、天候の全域作用と局所光・風・種を接続 |
| 天候 | 晴れ・薄曇り・小雨。初期晴れ、3正常解決投ごとに一期 |
| サイコロ | 1個、動的な6面、4系統×2入力レシピ |
| 意図 | 任意の系統／面の希望と方法選択、任意短文 |
| オラクル | オリジナル6枚、条件付きの短文と事実fallback |
| 表現 | 作用点に沿う光、少数の粒子、共通の鐘と自然音 |
| 記録 | 天候・配面・意図・出目・カード・状態・文章の自動保存 |
| 振り返り | 1回の詳細、観察グラフ、庭の状態の推移 |
| 運用 | オフライン、一台で起動・中断・再開・次の来場者へ |

カードごとの全面イラスト、複数バイオーム、自由建築、動物AI、クラフト、オンライン同期、音声文字起こし、実行時LLM、量子API、実績は後の拡張とする。種の水流／風輸送や動的な樹木の影も初期版では計算しない。

## 2. 3日を使う順序

| 時期 | 完了させたいこと | 続行判断に使う実物 |
|---|---|---|
| 1日目 | 展示端末とUnity版の確定、ビルド、初期晴れと1入力の状態更新・保存・再開。水の移動と吸水を先に確認 | Editorだけでなく端末で動く実行ファイル、再起動後の同じ庭と天候 |
| 2日目 | 三天候の合成、動的6面、4系統、成長、カード、実イベントに合う文章、光・音を接続 | 空の違いと複数回の入力が庭へ重なる一連の体験 |
| 3日目 | グラフ、来場者交代、長時間運転、文字と音量、保存障害・中断を確認し展示ビルド固定 | 実際の展示端末の通しプレイと持ち出せるビルド |

作業速度は環境・資産・実機状況に依存する。初日にビルドできなければ、依存を増やさず環境と最小ループの成立に集中する。グラフの凝った表示やカード絵を削っても、配面の事前固定、実際のモデル、出目の記録、中断復旧は削らない。

展示端末がMacならmacOSビルド、WindowsならWindowsビルドを使う。両方の実機がない場合は、未検証のOSまで展示対応済みとしない。スマホ・Steamの両展開を妨げない共通設計で始め、各プラットフォームの合格は別に記録する。

### 最初の実装で迷わない順序

| 段階 | 作る最小単位 | 次へ進む根拠 |
|---|---|---|
| G1・環境 | Unity project、固定カメラの1シーン、展示機向けbuild | 対象機で起動する実行ファイル |
| G1・記録 | 一つのrun、一つの未終端round、同一期の天候材料、保存済み材料からの復元 | 固定fixtureの天候・出目・終状態が再開後も一致 |
| G2・自然 | 基礎profile・map・天候profileを検証し、晴れの水から三天候合成へ進む | 単セル・全庭・天候参照の収支・状態が一致 |
| G2・抽選 | 現在天候と8入力の局所必要度、固定した6面、任意の意図 | 同じ保存byte列から同じ天候・面・入力・庭になる |
| G3・体験 | EXPERIENCEの画面状態、文章と共通焦点、履歴 | 初回から数投・履歴・中断再開・来場者交代が通る |

これはG1〜G3内の作業順であり、全工程を一つの巨大PRへまとめる指示ではない。各フェーズの実装・結果を確認して次へ進む。
参照JSONの結果や抽選列をゲームの出力として読み込まず、C#で計算して照合する。展示機が決まる前に全OSの署名・ストア設定を一度に完成させることを開始条件にしない。

## 3. フェーズと受け入れ条件

既存実験のP0～P11と混同しないよう、新企画はG0～G5と呼ぶ。1PRは一つの目的とし、実行した検証と残件を[PROGRESS.md](../../PROGRESS.md)へ追記する。これは後続実装の計画であり、G0で後続コードを作ったという意味ではない。

### G0 — 設計をリポジトリへ追加（今回）

- 要件、動的配面、空間モデル、カードと言葉、記録、共通Unity構成、段階計画を文書化する。
- READMEから設計へ到達でき、旧実験の凍結文書と役割を区別できる。
- 内部リンク、規則間の整合、変更範囲、差分を確認する。
- v0.2では局所重み、量・範囲・時間の違い、自然の数値例、24本の文章条件、乱数材料と中断回復の契約を具体化する。[VALIDATION.md](./VALIDATION.md)に設計計算と実装後の検証を区別してまとめる。
- v0.3では初期庭の配置候補、全庭の参照計算、初回から連続投擲までの画面状態と、run単位の一意性・文章の根拠選定を具体化する。
- v0.4では天候と局所入力の合成、期の保存、現在天候を使う配面、源別の入力と混合後の状態、28文と関係の表示を具体化する。旧profile/map/reportを履歴用に残す。
- 既存アプリの`pnpm typecheck`、`pnpm test`、`pnpm build`を実行し、結果を記録する。
- Unityの実装・動作・ストア申請を完了扱いにしない。

### G1 — Unityの足場と永続化までの細いループ

- `unity/DestinyGarden/`にUnityプロジェクトを作成。使用可能なUnity 6 LTSの正確なパッチと対応パッケージを固定する。
- 1シーン、Input Actions、純C# Core、application coordinator、local RNG、append writerを接続。
- portごとの汎用frameworkや永続head cacheは先に作らず、最初はjournal走査で復元する。
- 開発用の固定入力fixtureで、事前状態から更新後状態まで保存・再開を通す。まだ本番ゲーム完成とはしない。
- `PreparationStarted`から`Resolved`までのクラッシュ点、乱数材料が保存済みの中断、取消と取得の競合、不完全末尾のsegment継続をテストし、再抽選と同じ水の二重適用を防ぐ。
- 初期期もWeatherEntropyCommittedを通し、同じ期の材料再利用を実装。3Resolved境界で一度だけ次の期へ進み、取消・欠測・履歴・長押しで天候が変わらないことを確認する。
- 展示候補機で実行ファイルを起動する。可能ならこの時点でAndroidまたはiOSの一台も起動確認する。
- 成功条件: 正常終了に頼らず、再開後に同じrunと確定済み結果を取り戻せる。

### G2 — 庭と動的サイコロ

- [SIMULATION.md](./SIMULATION.md)の水・吸水・蒸発・光・風・種・成長を実装する。
- [GAMEPLAY.md](./GAMEPLAY.md)の配面生成、候補の状態重み、個数制約、公開・固定を実装。
- 同一入力fixtureで水の保存、岩の影響、乾湿差、成長の条件を確かめる。
- `simulation-fixtures.v0.2.json`の初期状態・端数・期待値をC#で照合。単セル一致後、一つの地図で水→水→光、過湿／乾燥時の風、種→光／光→種を確認する。
- [GARDEN_LAYOUT.md](./GARDEN_LAYOUT.md)の候補map・参照reportをC#で再計算する。G0のPython参照計算は、Unity/Core実装のこの受け入れ条件を済ませたものではない。
- [WEATHER.md](./WEATHER.md)の三天候を同じ自然更新へ入力し、weather-profile.v0.4とweather-reference-report.v0.4で合成順・追加実効量・現在天候のneedを照合する。晴れの自然算術を旧参照の対照にする。
- 排出口の能力だけで非水没を保証せず、最大量の水入力を200回続ける開発fixtureで全セルの水量・保存則・排出を確認する。通常抽選とは別の開発runとする。
- 小雨＋最大ダイス水も200投ずつ照合。天候・ダイスの注水を分けて保存し、収支はその合計で検査する。
- 意図の面集合とその回の基準確率、出目とカードを自動記録する。
- 成功条件: 4系統の入力が実状態へ作用し、配面から最終状態まで追跡できる。レシピ名だけが違う未実装入力を残さない。

### G3 — 展示用の表現・文章・記録画面

- 同じ場・イベントを参照してFXとSEを再生し、静かな余韻へ戻す。
- カード6枚、条件付き28文（既存24＋雨との重なり4）、事実fallback、直前重複の抑制を接続。事実に適合する焦点をカードが選び、文章・音・光で共有する。
- 天候名と局所入力名、空と作用点の強調を区別。天候の環境音を一層へまとめ、主焦点の数や鐘を追加しない。
- 初めての発芽・開花などは保存済みイベントから「庭の発見」として自動表示できる。確認ボタン、報酬処理、別の進行台帳は増やさない。
- 日記・1回の詳細・可変確率に対応する観察グラフ、JSON／CSV出力を実装。
- 庭の歩みに天候帯を追加。一投の詳細は開始状態・天候・ダイス入力の三つの入口、植物の詳細は同じ個体の段階履歴から作る。
- 展示モードは次の来場者用の新runを作成。過去の履歴を上書きせず、前の人の任意文章を通常画面に残さない。
- タップ操作、長押し操作、音量、文字サイズ、低刺激設定を確認する。
- [EXPERIENCE.md](./EXPERIENCE.md)の画面遷移を確認。面番号の意味の変化、前回の文と次の配面、演出省略、旧gestureの持越し、履歴を閉じたときの同じ配面を照合する。
- 成功条件: 起動から数投、履歴閲覧、中断、再開、次の来場者までを、展示端末で実行できる。

### G4 — スマホ製品化

- iOS／Androidそれぞれの実機、署名済みビルド、バックグラウンド／強制終了／更新を確認。
- 画面比、安全領域、日本語フォント、タッチの誤操作、熱・電池・音割れを確認。
- OSのファイル共有、保存の互換性、空き容量不足、破損の検出を確認。
- 権限・実際のデータ利用に合う説明、作品の権利情報、ストア素材を整える。
- 公開アカウント、識別子、署名鍵、審査は実環境で確認する。資格情報をソースへ置かない。
- 成功条件: **iOSとAndroidを個別に**ビルド・実機試験で合格と記録する。

### G5 — Steam製品化

- まずWindowsを対象としてマウス／キーボード、ウィンドウ切替、解像度・音量を確認。
- SteamのApp ID、depot、起動設定、ストアとビルドの確認を行う。
- 実績やSteam Cloudは採用する場合にadapterとして追加。基本ゲームをSteam API初期化へ依存させない。
- コントローラー、Steam Deck、macOS／Linuxをうたう場合はそれぞれ実機・対象環境で検証する。
- 成功条件: 対象OSが明示された配布ビルドで、購入後の起動・保存・再開が成立する。

## 4. 人が何度も確認しなくてよいようにする

実装時は、壊れると意味が変わる境界を自動検証する。

| 領域 | 自動検証の対象 |
|---|---|
| 配面 | 6面、IDの一意性、3系統以上、同系統3面以下、同レシピ2面以下、局所重みの根拠、同じ保存材料からの一致 |
| 乱数 | D6変換の棄却法、天候・配面・出目・カード・表示の分離、天候の重み合計256と固定消費、テストで外部APIを呼ばない |
| 意図 | 結果取得前の確定、該当面集合、可変`p_t`、p=0/1と自由文の扱い |
| 自然 | 天候＋ダイスの合計水収支、負値・容量・上限、排出口、乾湿差、光と風の合成・遮蔽、蒸発の二重消費防止、段階イベントの一度だけの発行 |
| 復旧 | 配面／出目の各保存段階での停止、取消競合、連打、材料の再利用、破損末尾、新segmentの回復中断 |
| 文章 | 条件外の開花・到達・経路文を選ばない、カード再抽選なし、fallback、当時と現在の区別、主焦点の数 |
| データ | exportから同じ履歴・グラフを復元、保存後の文章の不変、デモと通常runの分離 |
| 互換 | 実装済みの共通fixtureをMono／IL2CPP・各端末で実行し、差を報告 |

実機で人が確認するのは、庭の変化が読み取れるか、文字が読めるか、音・光が心地よいか、操作を迷わないか、連続運転時に支障がないかを中心にする。自動テストだけで芸術的な品質や実機性能を合格扱いにしない。

## 5. ビルドと性能の初期目標

- モバイルは30fpsを下限目標、デスクトップは60fpsを目標にする。どちらでも同じ40tickを解決する。
- 粒子数、影、解像度、Bloomを品質設定で調整し、ゲームの水量・確率・成長速度は変えない。
- 1投擲のCore計算と保存は計測し、入力が固まって見える時間が出るなら処理を分割する。フレーム時間だけを理由にtickを捨てない。
- 音・FX・フォント・カードの資産一覧と出所・ライセンスを保持し、展示用と製品版で不足を確認する。
- 目標端末型番、OS、解像度、ビルド番号、フレーム時間、熱、メモリ、保存容量を検証記録に残す。現段階で性能保証値や最低端末を確定しない。

## 6. 公開と展示の区別

Unityで対象プラットフォームのビルドを作る工程と、ストアに公開する工程は別に計画する。

- iOSのローカル完成ビルドはmacOS上のXcode工程が必要。[Unity公式](https://docs.unity3d.com/6000.0/Documentation/Manual/ios-environment-setup.html)
- Google Playの公開条件はアカウント種別・作成時期でも異なるため、対象アカウントのテスト要件を確認する。[Google公式](https://support.google.com/googleplay/android-developer/answer/14151465?hl=en)
- Steamは登録、ストア・ビルド確認、待機／Coming Soon条件を公開計画時に確認する。3日展示の成立条件にSteam一般公開を入れない。[Steam公式](https://partner.steamgames.com/doc/gettingstarted/onboarding)

日数・SDK要件は変化し得るため、公開前に公式の現行条件を再確認する。ここには過去の待機日数を固定の保証として書かない。
