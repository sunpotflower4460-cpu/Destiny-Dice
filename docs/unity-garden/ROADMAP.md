# 実装・展示・製品化の計画

2026-11-12 / G0設計 v0.8。残り約3日という目安は展示準備の制約であり、全プラットフォームの公開期限を保証するものではない。

現行のcontent・規則版・必須／任意の範囲は[CURRENT_DESIGN.md](./CURRENT_DESIGN.md)を先に読み、各領域の詳細へ進む。過去の設計版・参照reportは履歴として残し、新規runへ混在させない。

## 1. 展示で完成させる体験

**一つの庭で、空・届け先・動的な配面を見て振り、天候の中へ局所入力が加わる。場所の選択とそれまでの庭から、異なる育ち方と言葉と記録が残る。**

| 展示の必須範囲 | 上限・初期案 |
|---|---|
| 庭 | 1地図、固定カメラ、植物1種類、段階成長 |
| 届け先 | 入口・岩陰・ひらけた土の三地点。初期おまかせ、任意の固定選択は次の準備から継続 |
| 自然 | 水と土を中心に、天候の全域作用と局所光・風・種を接続 |
| 天候 | 晴れ・薄曇り・小雨。初期晴れ、3正常解決投ごとに一期 |
| サイコロ | 1個、動的な6面、4系統×2入力レシピ |
| 意図 | 任意の系統／面の希望と方法選択、任意短文 |
| オラクル | オリジナル6枚、条件付きの短文と事実fallback |
| 表現 | 作用点に沿う光、少数の粒子、共通の鐘と自然音 |
| 記録 | 天候・届け先設定・実作用点・配面・意図・出目・カード・状態・文章の自動保存 |
| 振り返り | 1回の詳細、観察グラフ、庭の状態の推移 |
| 運用 | オフライン、一台で起動・中断・再開・次の来場者へ |

三地点は同じ静的mapへ作用点を切り替える仕組みで、新しい地形を毎回生成しない。物理的な作用先と、その後の水・植物・配面の違いを優先する。実際の播種記録から一つの植物modelの色・花弁幅を変える表現は、[DIVERSITY.md](./DIVERSITY.md)の任意追加とし、この基本ループの後に取り組む。未採用の見た目を実装済みとせず、外見の差だけで物理的な多様性を確認したことにしない。

カードごとの全面イラスト、複数バイオーム、自由建築、動物AI、クラフト、オンライン同期、音声文字起こし、実行時LLM、量子API、実績は後の拡張とする。種の水流／風輸送や動的な樹木の影も初期版では計算しない。

## 2. 3日を使う順序

| 時期 | 完了させたいこと | 続行判断に使う実物 |
|---|---|---|
| 1日目 | 展示端末とUnity版の確定、ビルド、初期晴れ・一つの届け先・1入力の状態更新・保存・再開。水の移動と吸水を先に確認 | Editorだけでなく端末で動く実行ファイル、再起動後の同じ庭・空・場所 |
| 2日目 | 三天候・三地点と動的6面、4系統、成長、カード、実イベントに合う文章、光・音を接続 | 同じ入力でも作用点と履歴に応じて庭が変わり、今回／次からを迷わず読める体験 |
| 3日目 | グラフ、来場者交代、長時間運転、文字と音量、保存障害・中断を確認し展示ビルド固定 | 実際の展示端末の通しプレイと持ち出せるビルド |

作業速度は環境・資産・実機状況に依存する。初日にビルドできなければ、依存を増やさず環境と最小ループの成立に集中する。グラフの凝った表示、カード絵、出生時の色・幅の追加を削っても、場所・配面の事前固定、実際のモデル、出目の記録、中断復旧は削らない。三地点の入力と保存が未完成なら、多様な育ち方が完成したとはせず、成立した範囲を展示候補として記録する。

展示端末がMacならmacOSビルド、WindowsならWindowsビルドを使う。両方の実機がない場合は、未検証のOSまで展示対応済みとしない。スマホ・Steamの両展開を妨げない共通設計で始め、各プラットフォームの合格は別に記録する。

| G2・抽選 | 三地点の実作用先、現在天候と8入力の局所必要度、固定した6面、任意の意図 | 同じ保存byte列と場所設定から同じ天候・場所・面・入力・庭になる |

これはG1〜G3内の作業順であり、全工程を一つの巨大PRへまとめる指示ではない。各フェーズの実装・結果を確認して次へ進む。
参照JSONの結果や抽選列をゲームの出力として読み込まず、C#で計算して照合する。展示機が決まる前に全OSの署名・ストア設定を一度に完成させることを開始条件にしない。

## 3. フェーズと受け入れ条件

既存実験のP0～P11と混同しないよう、新企画はG0～G5と呼ぶ。1PRは一つの目的とし、実行した検証と残件を[PROGRESS.md](../../PROGRESS.md)へ追記する。これは後続実装の計画であり、G0で後続コードを作ったという意味ではない。

### G1 — Unityの足場と永続化までの細いループ

着手時は[CURRENT_DESIGN.md](./CURRENT_DESIGN.md)と[design-manifest.v0.8.json](./content/design-manifest.v0.8.json)を索引とし、採用するcontentと参照fixtureを区別する。manifestを置いたことだけでUnity loaderや保存互換が完成したとは扱わない。

- `unity/DestinyGarden/`にUnityプロジェクトを作成。使用可能なUnity 6 LTSの正確なパッチと対応パッケージを固定する。
- 1シーン、Input Actions、純C# Core、application coordinator、local RNG、append writerを接続。
- portごとの汎用frameworkや永続head cacheは先に作らず、最初はjournal走査で復元する。
- 開発用の固定入力fixtureで、事前状態から更新後状態まで保存・再開を通す。まだ本番ゲーム完成とはしない。
- `PreparationStarted`から`Resolved`までのクラッシュ点、乱数材料が保存済みの中断、取消と取得の競合、不完全末尾のsegment継続をテストし、再抽選と同じ水の二重適用を防ぐ。
- 初期期もWeatherEntropyCommittedを通し、同じ期の材料再利用を実装。3Resolved境界で一度だけ次の期へ進み、取消・欠測・履歴・長押しで天候が変わらないことを確認する。
- 届け先設定の保存とPreparationStartedを同じwriterで順序付ける。公開済みPreparedの場所・6面は不変とし、Ready／提示中の変更は次の準備へ使う。次の準備を提示終了前へ先行させず、Preparing中の入力を予約しない。保存済み材料と設定から、固定選択・おまかせ・中断再開を再現する。
- 通常の新runは静的mapから作り、同run復帰は保存snapshotを保持する。別runの庭のimport/forkはこの展示工程へ入れない。
- 初回作成は内容→RunCreationPlan→固定targetRunIdのRunStartedの順とする。plan途中・受理後・genesis途中・保存応答前の終了を実I/Oで確認し、初回から勝手に別runへ変わらないことを確かめる。障害後の新庭は明示操作とし、旧原本・未確定範囲を保全したrecoveryFresh計画から静的mapへ始める。完全に閉じられない旧runへRunClosedを偽造しない。
- 来場者交代はRunSwitchRequestedを保存して切替先を固定し、旧roundの決着・RunClosed・新RunStartedへ進む。要求保存後・旧run閉鎖後・新run開始後の停止から同じ切替先一つへ復帰し、起動projectionが旧本文を通常画面へ再公開しないことを確認する。要求未保存の終了を、交代受理・完了と見なさない。
- 展示候補機で実行ファイルを起動する。可能ならこの時点でAndroidまたはiOSの一台も起動確認する。
- 成功条件: 正常終了に頼らず、再開後に同じrunと確定済み結果を取り戻せる。

### G3 — 展示用の表現・文章・記録画面

- 同じ場・イベントを参照してFXとSEを再生し、静かな余韻へ戻す。
- カード6枚、catalog v0.7の28文、事実fallback、oracle-focus.v0.7を接続。順位はv0.5のカード対応・直近文比較・優先度を継承し、shadowed_budは同じ焦点セルのダイス追加光の実適用証拠を必要とする。全成立候補からの勝者を最大3groupの候補へ必ず残し、文章・音・光で同じ焦点を共有する。
- 順位を継承するoracle-selection-fixtures.v0.5の選定だけの例をC#で照合し、別にv0.7の実イベントから述語が成立する境界も確認する。追加光が届かない日陰のつぼみに、別セルの光を根拠として文章を出さない。合成された成立済み根拠の照合だけで、全文章機能の合格とはしない。
- 天候名と局所入力名、空と作用点の強調を区別。天候の環境音を一層へまとめ、主焦点の数や鐘を追加しない。
- おまかせを初期値にし、場所の必須選択を増やさない。「今回」と「次から」を同じ小さな欄で区別し、場所の説明を開く操作から設定を変えない。Ready／提示中／Preparingと保存の境界を通して、選択時点と実際に使った場所が一致することを確かめる。
- 土の湿り比と水面を別に描き、Readyでは公開済み天候の基礎場へ戻る。種の説明は公開中Preparedの開始状態から導き、抽選の不収録と空き不足を区別する。
- skip・中断・run切替で古い提示所有者と未再生cueを失効させる。保存済みの庭と本文を静かに復元し、飛ばした音を次の一投へまとめて鳴らさない。
- 初めての発芽・開花などは保存済みイベントから「庭の発見」として自動表示できる。確認ボタン、報酬処理、別の進行台帳は増やさない。
- 日記・1回の詳細・可変確率に対応する観察グラフ、JSON／CSV出力を実装。
- [OBSERVATION.md](./OBSERVATION.md)の共通投影を三つの画面とCSVへ使う。準備順の位置・初期点・単位・範囲・nullを揃え、既知材料だけの出目も比較へ含める。意図なし・該当面なし・結果未成立・未投擲の案内を[observation-fixtures.v0.8.json](./content/observation-fixtures.v0.8.json)で照合した後、実journalから同じ投影を作る。比較対象0件を0%として表示しない。
- 一投のつながりは保存済みの同cell/tickの根拠を使う。正の風と成長が同じtickにあっても、実蒸発0なら土が乾いた説明を付けない。成熟・成長0・旧版で局所根拠がない場合も、確認できる入力と終状態をそのまま読めるようにする。
- 庭の歩みに天候帯と実際の届け先を表示。一投の詳細は開始状態・天候・確定場所へのダイス入力を入口とし、植物の詳細は同じ個体の播種位置・出生条件・段階履歴から作る。
- 基本動作の後、出生時の見た目を採用する場合は、実際のSeedPlacedの水分比による三配色と三天候による花弁幅を一つの植物modelへ対応させる。使用profileをrunへ固定し、初期植物は中立、記録のない出生条件は推測しない。色・幅を毎投の空で変えず、成長量・能力・既存28文の意味は変えない。採否と実機で確認した範囲をビルド記録に残す。
- 展示モードは次の来場者用の新runを作成。保存済みRunSwitchRequestedから復帰した場合も中立の切替画面を使い、旧runの結果・本文を通常画面へ再公開しない。過去の履歴を上書きせず、保存障害時は同じ切替を回復する。運営は新しい庭が公開されてから次の来場者へ渡す。
- タップ操作、長押し操作、音量、文字サイズ、低刺激設定を確認する。
- [EXPERIENCE.md](./EXPERIENCE.md)の画面遷移を確認。面番号の意味の変化、前回の文と次の配面、演出省略、旧gestureの持越し、履歴を閉じたときの同じ配面を照合する。23場面は同書§9.1の証拠区分へ対応させ、機械的な条件を自動化し、人はH1〜H5の通し確認を行う。§9.2のV1〜V3で、実状態の差を読めることと、細かな差を誇張しないことを確かめる。
- 成功条件: 起動から数投、履歴閲覧、中断、再開、次の来場者までを、展示端末で実行できる。

### G4 — スマホ製品化

- iOS／Androidそれぞれの実機、署名済みビルド、バックグラウンド／強制終了／更新を確認。
- 画面比、安全領域、日本語フォント、タッチの誤操作、熱・電池・音割れを確認。
- OSのファイル共有、保存の互換性、空き容量不足、破損の検出を確認。
- 権限・実際のデータ利用に合う説明、作品の権利情報、ストア素材を整える。
- 公開アカウント、識別子、署名鍵、審査は実環境で確認する。資格情報をソースへ置かない。
- 成功条件: **iOSとAndroidを個別に**ビルド・実機試験で合格と記録する。

### G5 — Steam製品化

- まずWindowsを対象としてマウス／キーボード、ウィンドウ切替、解像度・音量を確認。
- SteamのApp ID、depot、起動設定、ストアとビルドの確認を行う。
- 実績やSteam Cloudは採用する場合にadapterとして追加。基本ゲームをSteam API初期化へ依存させない。
- コントローラー、Steam Deck、macOS／Linuxをうたう場合はそれぞれ実機・対象環境で検証する。
- 成功条件: 対象OSが明示された配布ビルドで、購入後の起動・保存・再開が成立する。

## 4. 人が何度も確認しなくてよいようにする

実装時は、壊れると意味が変わる境界を自動検証する。

| 領域 | 自動検証の対象 |
|---|---|
| 配面 | 6面、IDの一意性、3系統以上、同系統3面以下、同レシピ2面以下、局所重みの根拠、同じ保存材料からの一致 |
| 乱数 | D6変換の棄却法、配面用材料からの地点選択と材料消費の規則、天候・配面・出目・カード・表示の分離、天候の重み合計256と固定消費、テストで外部APIを呼ばない |
| 届け先 | 三地点の作用範囲、設定保存と準備の順序、公開後の不変、今回／次から、おまかせの再現、空き不足で自動移動しないこと |
| 意図 | 結果取得前の確定、該当面集合、可変`p_t`、p=0/1と自由文の扱い |
| 自然 | 天候＋ダイスの合計水収支、負値・容量・上限、排出口、乾湿差、光と風の合成・遮蔽、蒸発の二重消費防止、段階イベントの一度だけの発行 |
| 復旧 | 初回作成計画とgenesis、配面／出目の各保存段階での停止、取消競合、連打、材料の再利用、破損末尾、新segmentの回復中断、保存済み庭切替・明示的な救済から同じ先への収束 |
| 文章 | 条件外の文を除外、カード再抽選なし、直近比較と3groupの勝者保持、fallback、主焦点と必須補助 |
| 表示 | 湿り比・地表水・段階の対応、地点ごとの種の範囲、成熟庭、skipと旧cue、低fpsと消音での同じ終状態。任意の出生時の見た目は出自と固定profileとの一致 |
| データ | JSON exportから同じ履歴・共通投影を復元、横軸・初期値・null・比較対象0件、保存後の文章の不変、デモと通常runの分離 |
| 関係の根拠 | 同cell/tickの蒸発・成長をスカラー再計算し、実蒸発0・地表だけの蒸発・成長上限・参照不一致で過剰な因果説明を作らない |
| 互換 | 実装済みの共通fixtureをMono／IL2CPP・各端末で実行し、差を報告 |

実機で人が確認するのは、庭の変化が読み取れるか、文字が読めるか、音・光が心地よいか、操作を迷わないか、連続運転時に支障がないかを中心にする。[EXPERIENCE.md](./EXPERIENCE.md)§9.1のH1〜H5へまとめ、自動化できる入力・projection・cue列の条件を毎回手作業で繰り返さない。実際のI/O・OS中断・来場者交代は対象端末で確かめる。自動テストだけで芸術的な品質や実機性能を合格扱いにしない。

## 5. ビルドと性能の初期目標

- モバイルは30fpsを下限目標、デスクトップは60fpsを目標にする。どちらでも同じ40tickを解決する。
- 粒子数、影、解像度、Bloomを品質設定で調整し、ゲームの水量・確率・成長速度は変えない。
- 1投擲のCore計算と保存は計測し、入力が固まって見える時間が出るなら処理を分割する。フレーム時間だけを理由にtickを捨てない。
- 音・FX・フォント・カードの資産一覧と出所・ライセンスを保持し、展示用と製品版で不足を確認する。
- 目標端末型番、OS、解像度、ビルド番号、フレーム時間、熱、メモリ、保存容量を検証記録に残す。現段階で性能保証値や最低端末を確定しない。

## 6. 公開と展示の区別

Unityで対象プラットフォームのビルドを作る工程と、ストアに公開する工程は別に計画する。

- iOSのローカル完成ビルドはmacOS上のXcode工程が必要。[Unity公式](https://docs.unity3d.com/6000.0/Documentation/Manual/ios-environment-setup.html)
- Google Playの公開条件はアカウント種別・作成時期でも異なるため、対象アカウントのテスト要件を確認する。[Google公式](https://support.google.com/googleplay/android-developer/answer/14151465?hl=en)
- Steamは登録、ストア・ビルド確認、待機／Coming Soon条件を公開計画時に確認する。3日展示の成立条件にSteam一般公開を入れない。[Steam公式](https://partner.steamgames.com/doc/gettingstarted/onboarding)

日数・SDK要件は変化し得るため、公開前に公式の現行条件を再確認する。ここには過去の待機日数を固定の保証として書かない。
