# Destiny Garden — Unity箱庭ゲーム設計

設計版: **0.8 / 2026-11-12**

段階: **G0 設計。Unityの実装・実機検証・ストア公開はまだ行っていない。**

作業名: Destiny Garden（正式な作品名は未定）

**届ける場所、空の状態、庭の積み重なりから、次のサイコロの6面が生まれる。意図を添えて振ると、天候の中へ水・風・光・種が加わり、それぞれの庭の変化と短い言葉が返ってくる。**

## v0.8で整えた、始まりと振り返り

最初の庭を開くところから、後で出来事を読み返すところまで、保存した事実と表示の対応を具体化する。

- **初めての起動も、同じ庭へ戻る。** 不変の作成計画を保存してからrunを作り、途中終了は同じID・初期状態・内容へ収束させる。障害後に新しい庭へ移る場合も、明示した操作と旧原本を残し、失われた記録が復旧した扱いにしない。
- **三つの記録画面を一つの投影へ。** [OBSERVATION](./OBSERVATION.md)で横軸、初期点、水量と成長量、対象範囲を揃える。確定した成長0、まだ解決していない庭、既知の出目をそれぞれ区別する。
- **意図を添えない遊びにも、自然な記録の入口を。** 庭の歩みはそのまま残る。比較対象がないときは短い案内を出し、0%の成功率や失敗数へ置き換えない。カードや提示記録が欠けても、分かっている出目を消さない。
- **風・湿り・成長を、同じ瞬間の根拠でつなぐ。** 既存の成長イベントに、同じcell・tickの場・蒸発前後・端数・成長前後を残す。風が届いた回でも、実際の蒸発が0だったり地表水だけが減ったりした場合は、その違いを説明へ反映する。

自然係数、三地点、天候・出目・カードの確率、28文と順位は維持する。小さな[投影例](./content/observation-fixtures.v0.8.json)と[局所計算例](./content/growth-witness-fixtures.v0.8.json)を追加し、保存済み記録からの実装・端末のI/O・画面の検証はG1〜G3で行う。通常プレイの必須操作は増やさない。

## v0.7で整えた、全体の接続

遊びの要素を増やす前に、最初の一投から連続プレイ、記録、来場者交代までを同じ仕様で実装できるようにする。

- **現行の採用候補を一つの索引へ。** 基礎v0.2・map v0.3・天候v0.4・場所v0.6の組合せを保持し、[manifest](./content/design-manifest.v0.7.json)で原本とhashを固定する。参照reportとゲームへ採用するcontentを分け、旧anchorを現行の三地点へ混ぜない。
- **交代の途中で終了しても、同じ次の庭へ。** 交代要求と次run IDを保存し、旧roundの処理・旧runの閉鎖・新run作成の中断から回復する。旧処理の結果は保持し、交代受理後の通常画面へ前の人の本文を戻さない。
- **文章と光の対象を揃える。** [catalog v0.7](./content/oracle-catalog.v0.7.json)では、「岩陰のつぼみは、まだ閉じたままでした。」にも同じ場所へ光が届いた根拠を必須にする。他の27entryと、カード対応・直近の未使用・priorityの順位は維持する。
- **三地点の長期注水を別に確認する。** 同じ強制小雨と水入力を、入口・岩陰・ひらけた土へそれぞれ重ねる[参照計算](./content/water-stress-reference-report.v0.7.json)を追加する。旧入口の結果を、新しい作用点の検証結果として扱わない。
- **人が見る項目を絞る。** 入力競合・保存参照・cue列は自動照合へ、実端末の中断は運用確認へ、見やすさ・日本語・光と音は人の確認へ整理する。「いま振る一投」と、その後に適用する場所設定の説明も揃える。

自然の係数、天候と出目・カードの確率、必須操作は変えない。今回もG0の設計更新であり、Unity実装と実機での美しさ・操作の検証は後続ゲートで行う。

## v0.6で加えた、それぞれの育ち方

一つの地形でも、どこへ何を重ねたかが違えば、水分、種の配置、成長、その後の6面が変わるようにする。

- 届け先を入口・岩陰・ひらけた土の三つへ広げる。その回の水・風・光・種の中心を同じ場所へ置き、既存の数式で周囲へ作用させる。
- 既定の「おまかせ」では保存した配面材料から場所も選び、追加操作なしで遊べる。任意の場所変更は公開中の一投を保ち、その後に準備する回から持続する。
- 公開中の場所と6面は変えない。変更は「次から」と表示し、演出中の先行準備を止めることで、次回の指定が準備に追い越されないようにする。
- 種を置いた時の実際の土と天候から、三色×三花弁幅の外観を導く。花になった後も基準外観を保ち、植物の能力や成長には影響させない。G3で扱う小さな表示拡張とする。
- 同じrecipeで場所だけを変える比較と、同じ材料列でプレイ方針を変える比較を分ける。物理的な配置と粗い空間状態を数え、IDだけの違いを多様性へ数えない。

## v0.5で磨いた継続する体験

同じ庭を何回か振ったあとにも、変化の意味を読み取り、静かに眺め続けられるようにする。

- 文章は28本の本文と成立条件を維持。同じカードとの対応なら、最近使っていない成立文をpriorityより先に選ぶ。最大3groupへ絞る途中でも、その勝者が落ちないよう選定順を統一する。同じ事実しかない回は同文を使える。
- 今回の6面に種がない理由を、抽選で選ばれなかった場合と、種が届く範囲の空き不足に分ける。任意の説明で範囲を見られ、目標の選び直しは求めない。
- v0.5の固定anchorでは追加できる種は最大17個、初期分を含む植物は21個。種の範囲を使い切っても空き土34セルが残るため、「庭全体がいっぱい」とは表示しない。v0.6の範囲はGARDEN_LAYOUTの三地点で別に確認する。花になった個体も残し、水・風・光・天候を眺め続けられる。
- 土の湿りは容量に対する水分比、水面は地表水、植物の形は保存された段階から描く。浅い土と深い土でも、モデルが見ている湿りと表示の関係を揃える。
- 演出を省略・中断したら、未再生の音や注目の光は破棄し、保存済みの庭と本文へ静かに戻す。古い一投の音を次の空へ持ち越さない。

## v0.4でつないだ関係

- 晴れ・薄曇り・小雨を、全域の光・風・実際の雨入力として庭へ加える。天候の中でダイスの局所入力が働き、同じ出目でも条件によって違いが生まれる。
- 一つの天候は正常に解決した3投ぶん続く。初期は晴れ、その後は専用の保存済み材料から選ぶ。天候と6面を公開してから意図を添えられ、待機・祈り・取消・再開で天候を引き直さない。
- 光と風は天候とダイスを合成し、上限と遮蔽を一度適用。配面の光の必要度は、今回の天候から判断する。
- 水分・成長・端数・植えた場所は次の投擲へ残る。種が空き土を使うことで、次の種候補と配面にも影響する。
- 文章は既存24本に、同じ場所・時点で雨と光・風・種・発芽が重なった4本を追加。言葉・カードの焦点・光・SEを同じ根拠へ合わせる。
- 関係図を開始時の庭・天候・サイコロ入力の三つの入口にする。庭の歩みに天候帯、植物の詳細に同じ個体の段階履歴を添える。

[天候profile](./content/weather-profile.v0.4.json) · [天候を含む参照結果](./content/weather-reference-report.v0.4.json) · [28文のcatalog](./content/oracle-catalog.v0.4.json)

v0.4時点では、数値の基礎profile v0.2、静的map v0.3、天候拡張・配面・文章選定v0.4を組み合わせた。新しいrunでは基礎profile・map・天候profile・deck・catalogの実体hashを固定する。天候の追加はG0の設計であり、Unityの天候表示・実機の音・操作の実装はこれから行う。

## v0.3で具体化したこと

一投ごとの規則を、**どんな庭で、どの順番に見せ、次にどう触れるか**へつなげる。

- 初期庭を16×16の配置データへ落とし、水の入口・岩・排出口・乾湿・光・種の位置を共有する。
- 単セルの算術に加え、全庭での固定入力と、補正しない複数の抽選列を設計用に照合する。Unity実機の結果とは分けて記録する。
- 面番号への意図と系統への意図を区別し、次の配面で中身が変わっても目標を自動変更しない。
- 結果の提示、余韻、次の6面の公開をつなげ、前回の言葉が次の結果に見えない構成にする。
- 同runの並行投擲、文章の根拠対象の同点、全域の水流集約を見直し、同じ保存入力からの再現性を強める。

新しい遊びの必須操作は増やさず、基本はサイコロを押して離す一操作のままにする。詳細と図はEXPERIENCE.mdとGARDEN_LAYOUT.mdを入口に読む。

## v0.2で強化した体験と仕組み

**同じ入力でも、届く場所と、それまでの庭の積み重ねで意味が変わる。** この軸を、実装者が判断し直さずに作れる規則へ具体化した。

| 強化点 | 体験への効果 |
|---|---|
| 庭全体の平均から、各レシピが実際に働く場所の状態へ配面判断を変更 | 遠くの乾燥だけを理由に、湿った入口へ水を増やす偏りを避ける |
| しずく／雨は同じ総水量で、集中・広がり・時間を変える | 多い方を引けばよいという単調さを減らす |
| 風・蒸発・湿り・成長の数式を接続 | 湿りすぎた土では風が助けになり、乾いた土では別の結果になる |
| カードが、実際の出来事の中から注目する変化を選ぶ | カードの意味と、短い言葉・光・音が一つの焦点を持つ |
| 同時に強調する出来事と音の数を制限 | 多くのセルが変化しても、静けさと読みやすさを保つ |
| 乱数材料の保存、取消の順序、不完全な保存からの復旧を具体化 | 再起動で配面・出目が変わらず、手動の確認作業を減らす |

数値例と文章を、編集できる設計資料として同梱する。これらは`designCandidate`であり、Unityが既に読み込んで動いているデータではない。

- [simulation-profile.v0.2.json](./content/simulation-profile.v0.2.json): 計算単位、係数、入力の量・範囲・時間。
- [simulation-fixtures.v0.2.json](./content/simulation-fixtures.v0.2.json): 初期状態と期待値を持つ参照算術の例。
- [oracle-catalog.v0.2.json](./content/oracle-catalog.v0.2.json): オリジナル6枚と、成立条件を持つ24本の日本語短文。

設計上の計算例を確認したことと、Unity実装・全庭の連続運転・端末間の一致を確認したことは区別する。確認範囲は[VALIDATION.md](./VALIDATION.md)にまとめる。

## 実装を始めるための初期判断

以下はユーザーが細部まで指定した値ではなく、**実装用の初期案**である。試作結果から調整し、実際に採用した値をルール版とともに保存する。

- 初期入力は水・風・光・種の4系統、各2レシピ。6面は毎回この候補から構成する。
- 天候は晴れ・薄曇り・小雨の3種類。初期晴れ、3正常解決投ごとに次の期へ進む。天候名・量・重みは候補profileへ固定する。
- 配面を表示してから意図を確定する。配面決定に意図・祈りの方法・過去の的中率を使わない。
- 6面からの出目は論理抽選で各1/6。立体サイコロはその結果を表現する。
- 庭は16×16の固定格子を3Dで表示する。モデルは1投擲ごとに固定tick数だけ進める。
- 自然への作用点は三つの検証済み地点から決める。おまかせで始まり、場所指定は任意。今回の場所・6面を保存してから公開する。
- 最初はオフラインのローカル乱数・ローカル保存・同梱文章で完結させる。
- 展示は横画面を基準とする。モバイル製品はiOS／Android、Steam製品の最初の対象OSはWindowsを初期案とする。
- macOSは展示端末として選択可能。SteamのmacOS／Linux対応とSteam Deckの検証は別の合格項目とする。
- カードはオリジナル6枚を復元抽選。同じカードが連続しても引き直さない。
- 実行時の生成AI、音声認識、オンライン量子乱数、Steam Cloudは拡張点として設け、展示の依存条件にしない。

「毎回生成する」は「必ず前回と違う配面になる」という意味ではない。自然な抽選で同じ配面になることも認める。

## 体験の完成像

庭を見ると、今回は水が多いサイコロになっている。水を願う設定のまま、サイコロに触れて、離す。出目に対応した水が庭へ入り、同じ流れの計算で岩を避けて動き、土の空き容量に応じて染み込む。

根元での吸水が記録された回には、小さな鐘と光のあと、「根元の土に、水が染み込みました」と短い言葉が残る。カードの意味や詳しい記録は、見たいときだけ開ける。

数回後、十分な水と光が重なった場所でつぼみが開く。その成長は過去の状態を使った計算で生じる。履歴から、どんな入力が来て、どこが変わったかを振り返れる。開花・到達などの文章は、それに対応するモデル上の出来事が記録された場合だけ表示する。

## 既存Intention Diceとの関係

既存の[DESIGN.md](../../DESIGN.md)と[PROTOCOL_FREEZE.md](../../PROTOCOL_FREEZE.md)は、React／Capacitor製の1年間の実験アプリについて定義している。現在の1024～4096ビットの測定を、このゲームのD6抽選へ読み替えない。

| 引き継ぐ考え方 | Unityで新しく設計する部分 |
|---|---|
| 意図の先行記録、実際の乱数ソース記録 | 動的な配面、6面からの公平な抽選 |
| 追記履歴、single writer、エクスポート | 庭の状態、自然入力、出来事、表示文 |
| UIと計算の分離、決定的なテスト | 純C#の空間モデルとUnityの表示 |
| 観察と確証の区別 | 各回の配面に対応する基準確率 |

Unity側は新しい`gameId`・`runId`・保存領域を持つ。既存実験の登録内容、台帳、統計式、プロトコルを変更しない。TypeScriptの実装をそのままUnityへコピーせず、必要な契約と検証例を参考にC#へ実装する。既存実験データのUnityへの移行は今回の範囲に含めない。

この文書群は旧実験の凍結規則を上書きするものではない。将来のUnity実装は人間から指定されたフェーズごとに行い、[AGENTS.md](../../AGENTS.md)の1PR・1目的、実行結果による検証、PROGRESS追記を守る。

必須要件は上のR01～R12。数値・名称・操作時間は初期案であり、`ruleset`／contentのバージョンに含める。保存・抽選順序は[DATA_CONTRACT.md](./DATA_CONTRACT.md)、自然モデルは[SIMULATION.md](./SIMULATION.md)をそれぞれの詳細の正とする。
